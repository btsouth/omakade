## Resource and architecture safety

- **Never run ARM builds or ARM emulation on this workstation.** ARM validation is owned by
  interested contributors on suitable hardware.
- Do not compile while a game or emulator is running. Recheck system load and available memory;
  never stop or interfere with the maintainer's emulator or VM processes.
- Local x86 compilation must remain low priority, single-job, and hard-capped. The working guard
  used `CPUQuota=100%`, `MemoryHigh=3G`, `MemoryMax=4G`, `MemorySwapMax=0`, `nice -n 15`,
  `ionice -c3`, and `-j1`.
- Full-suite runs are milestone checks, not a per-edit loop. Use focused tests during development.
- The pending WUA profile change in the post-1.8 checkout is now committed as `c6bd6bc`;
  the integrated branch already contained that extension and now includes its regression test.

## RomM continuation

Track this work in
[SBS-1157](https://linear.app/southboundsoftware/issue/SBS-1157/add-a-read-only-romm-library-source).
The product boundary is intentionally narrow:

1. Store a RomM Client API Token with `roms.read` scope in libsecret; never write it to
   `config.toml`, logs, SQLite, or personal backup archives.
2. Fetch bounded pages from `GET /api/roms` with same-origin redirects only and retain the last
   complete SQLite catalog when a refresh fails.
3. Resolve `files` or `fs_path`/`fs_name` only through the configured local mount. Do not download,
   stream, delete, or modify RomM content.
4. Add `RomMGameModel`, source diagnostics, source filters, console-card participation, and local
   launch dispatch through Omakade's existing emulator resolution.
5. Add isolated pagination, authentication, cache-retention, source-role, dedicated-emulator,
   settings, and desktop/Couch fixtures. Cover downloads remain optional follow-up work.

RomM's API paths are server-relative, not client launch paths. A locally mounted library root is
therefore required for this phase.
