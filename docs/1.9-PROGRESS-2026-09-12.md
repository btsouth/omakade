## RomM catalog transport and credentials

`RommCatalog` adds GET-only paginated catalog fetching and a separate SQLite cache.
Requests use a Client API Token, manual same-origin redirects, no shared cookies or
HTTP cache, a 15-second transfer timeout, a two-minute refresh deadline, bounded
page/total bytes, and bounded pages and records. Unexpected offsets, changing totals,
duplicate IDs, malformed data, and stalled pagination fail the refresh. SQLite replaces
one server/mount catalog transactionally only after all pages complete.

Failures, cancellation, and failed SQLite inserts preserve the previous catalog. Cached
launch paths are checked against the current mount before returning records. Remote
content is never downloaded, modified, or deleted. Cover references remain metadata;
this client does not fetch covers.

`RommCredentials` stores and retrieves Client API Tokens through libsecret, scoped to
the normalized server URL and serialized with the app's existing keyring lock. Its
blocking methods must run on a worker when the UI is connected. Tokens are not written
to configuration or the catalog. Tests reject malformed credentials without accessing
the user's keyring. Live keyring acceptance is still required with the future settings UI.

The current [RomM API authentication documentation](https://docs.romm.app/5.0.0/developers/api-authentication/)
defines Client API Tokens as `rmm_` plus 64 hex characters and requires `roms.read` for
catalog reads. The [upstream catalog endpoint](https://github.com/rommapp/romm/blob/master/backend/endpoints/roms/__init__.py)
uses offset/limit pagination and permits a null total. The parser now accepts that form
as an unknown total. Offset pagination cannot guarantee a snapshot when the server
changes in ways that preserve total and unique IDs; a later refresh reconciles such changes.
